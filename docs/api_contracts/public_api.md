# Aura Public Backend API

This is the final public HTTP surface for
`feat/backend-real-holdings-dynamic-allocation`. It is generated by FastAPI as
18 paths and 23 operations. All private resources are Bearer-authenticated and
owner-scoped unless noted as public.

## Holding write and compatibility contract

`PUT /api/portfolios/{portfolio_id}/holdings` changed from an authoritative
weight replacement to a complete ordered real-holding replacement. Each input
contains:

| Field | Meaning |
| --- | --- |
| `symbol` | One of Aura's 17 user-selectable USD-quoted assets |
| `invested_amount` | Positive amount originally invested; provenance, not current value |
| `invested_currency` | `USD` or `THB`; defaults to `USD` |
| `shares` | Positive aggregate share/coin quantity |
| `purchase_date` | Non-future purchase date |

The request order becomes the backend-controlled `position`. Symbols must be
unique. Real holdings persist `weight = NULL`; they do not persist current
price, value, allocation, or FX.

During the temporary compatibility period, a returned holding is exactly one
of:

- `LEGACY`: `weight` present and all real fields `null`/absent;
- `REAL`: `weight` is `null` and every real field is present.

Legacy portfolios remain available for list, detail, rename, duplication,
deletion, legacy reporting, and legacy simulations. Current valuation is not
available for legacy portfolios. A normal `PUT` replacement is the explicit
legacy-to-real conversion. Duplication preserves the source mode.

## Current valuation

`GET /api/portfolios/{portfolio_id}/valuation` accepts
`currency=USD|THB`; the default is `USD`.

All supported user assets are USD-quoted. For each holding, the backend uses
the latest persisted observation on or before the requested current date:

```text
current_value_usd = shares × asset_price
current_allocation = current_value_usd / total_current_value_usd
```

Required observations may be at most four calendar days old. USD valuation is
independent of FX. THB display additionally uses the internal `THB=X` series,
interpreted as USD/THB (THB per USD). `THB=X` is covered by default/scheduled
market updates but is not a user-selectable holding.

The response includes requested/display currency, requested date, oldest and
newest asset price dates, canonical USD total, display total, optional FX
context, and ordered holding facts/prices/values/allocations.

## Analytics semantics and reports

For real portfolios, analysis resolves the current USD dynamic allocation and
applies that fixed allocation to the user-selected historical period using the
existing periodically rebalanced analytics engine. It does not replay shares,
infer historical ownership, or use `purchase_date` to change the analysis
period. No analytics formula changed.

Individual asset return, volatility, maximum drawdown, and Sharpe describe the
asset. Portfolio risk contribution also depends on portfolio weights and
covariance/correlation. A larger investment does not make an asset inherently
more volatile, though a larger allocation can increase its portfolio risk
contribution.

`POST /api/portfolios/{portfolio_id}/reports` keeps `AnalysisPeriod`
(`start_date`, `end_date`) as its JSON body. The optional query parameter
`currency=USD|THB` defaults to `USD`.

Report versions are exact:

- `portfolio-analysis-response-v1`: legacy report behavior;
- `portfolio-analysis-response-v2`: real-holding report with frozen valuation
  context.

V2 freezes valuation currency/date, price dates, canonical USD and display
totals, optional FX, holding facts, prices, values, dynamic allocations,
complete analytics, per-asset metrics, and risk contribution/rank. Report
detail is version-aware. Opening a saved report reads its JSONB snapshot and
never revalues the portfolio.

## Simulations and immutable history

The three simulation POST request contracts are unchanged. A historical
scenario accepts `scenario_id`. Allocation Change accepts an explicit
historical period and `modified_allocation`; Combined accepts `scenario_id`
and `modified_allocation`.

For real portfolios, the original allocation is the current canonical USD
dynamic allocation at execution. The modified allocation remains the user's
hypothetical percentage input. Simulations continue to test fixed allocations
against historical prices and are not historical share-count backtests.

Existing V1 history remains readable. Exact V2 versions are:

- `historical-scenario-simulation-response-v2`
- `allocation-simulation-response-v2`
- `combined-simulation-response-v2`

V2 history freezes the current valuation baseline used when the simulation was
created. History detail restores that snapshot without current market data,
revaluation, or rerunning the simulation.

## AI contract and grounding

The public AI request and response shapes are unchanged. Grounding selects:

- live legacy portfolio: saved weights;
- live real portfolio: current USD valuation and dynamic allocation;
- saved Report V2: frozen report snapshot;
- saved Simulation V2: frozen simulation snapshot.

Saved resources do not require current prices. The agent explains
backend-owned results; it does not calculate financial truth, give personalized
advice, or issue buy/sell recommendations. Provider credentials and provider
implementation details are not part of the public contract.

## Error semantics

| Status | Established meaning |
| --- | --- |
| `401` | Authentication is missing or invalid |
| `404` | A private resource is missing or belongs to another user |
| `409` | Holding state is mixed, incomplete, unsupported, or incompatible with the requested operation |
| `422` | Request validation failed or the established historical analysis/simulation input is unprocessable |
| `503` | Required current asset data is missing/stale, or THB was requested and required FX is missing/stale |
| `500` | Sanitized unexpected internal failure |

Some established routes expose additional intentional statuses, such as AI
provider failures. Consult generated OpenAPI and route-specific tests before
treating the table as exhaustive.

## Transaction boundary

Repositories and services do not own commits. Successful writes commit at the
outer API/request boundary. Valuation is read-only. Reports and simulations
persist one immutable snapshot only after successful calculation at that outer
boundary; failures do not commit partial snapshots.
