# Aura Public Backend API

This is the current public HTTP surface. It is generated by FastAPI as
33 paths and 44 operations. Account-owned resources are Bearer-authenticated
and owner-scoped; shared market/asset status endpoints also require authentication.

## Market-data refresh status

`GET /api/market-data/status` requires Bearer authentication and migration
`d6e8f0a2b4c6`. It describes shared market observations and operational health,
not account-owned portfolio data. It never starts a worker, downloads prices,
or writes state. See [market-data status contract](market_data.md#daily-refresh-status)
and [deployment worker guide](../development/market-data-worker.md).
Database/status failures return sanitized `503`, not a healthy fallback.

## In-app notifications V1

Requires migration `c3d5e7f9a2b4` after `b9e4d2f7c1a6`. There is no
phone/browser push, email delivery, device token, background task, price alert,
or client-authored notification creation endpoint.

New successful report and simulation API saves record their notification in
the same caller-owned transaction before the single commit. A failure rolls
back both. All portfolio modes and all three simulation types are supported;
existing history is not backfilled. One saved result has at most one
notification, enforced by unique target keys. Ownership and exact portfolio/
resource association are verified without restoring or recalculating snapshots.
Messages are generic and contain no portfolio names, balances, holdings, or
snapshot data. Deleting a result, its portfolio, or its account cascades the
related notifications; account deletion also cascades its preferences.

`GET /api/notifications?limit=25&offset=0` returns `items`, `total`, and
`unread_count` for the authenticated account. Limit is 1–100; offset is
0–10000. Counts cover the whole inbox, not just the page. Items are ordered by
`created_at` descending then UUID descending and expose `id`, `kind`
(`analysis` or `simulation`), `title`, `message`, `portfolio_id`, `resource_id`,
`created_at`, and nullable `read_at`. Resource IDs identify the exact frozen
report or simulation, not the latest portfolio analysis. Empty inboxes return
empty items and zero counts. Counts and items can change between requests.

Both preference endpoints return `enabled`, `analysis_enabled`, and
`simulation_enabled`. PUT requires all three strict booleans and rejects
unknown body fields. Missing stored preferences default all three On without
writing on GET. Preferences belong to the account, survive logout/login, and
are not reset by client-local reset. Master Off or category Off suppresses
future events; previously received notifications remain readable. Re-enabling
does not recreate suppressed events. Full replacement is last-write-wins.

Read mutations return empty `204`. Missing/unowned notification IDs return
the same safe `404`; marking one read again preserves its original read time.
Mark-all is owner-scoped and does not remove notifications. Authentication,
validation, and sanitized unexpected failures use existing `401`/`422`/`500`
conventions and request-owned rollback. No user ID override is accepted in
request bodies. Clients refresh on entry/return and poll only in the foreground;
external notification permission is neither requested nor needed.

Clear mutations also return empty `204`. Clearing one missing/unowned ID uses
the same safe `404`; clearing an already-empty inbox succeeds. Clear-all covers
the entire account inbox, not just the visible page, and cannot affect another
account. Only notification rows are removed: portfolios, reports, simulations,
and preferences stay unchanged. No additional migration is required beyond
the existing notification V1 migration. Web and mobile require themed danger
confirmation before either clear action, then refresh inbox counts and badges.
Their notification navigation icons show a small red top-corner dot only when
the account has unread notifications; zero or unknown counts show no dot.

## Current asset forecasting

`GET /api/forecasting/assets/{symbol}/outlook` requires the existing Bearer
authentication. Symbols are trimmed and uppercased against Aura's 17-asset
registry. The route has no request body, portfolio context, configurable horizon,
or historical/as-of query parameter.

The response contains `symbol`, `forecast_origin_date`, fixed `horizon_days=30`,
`expected_return_30d`, and `forecast_realized_volatility_30d`. Each target has a
nested prediction interval (`return_prediction_interval` and
`volatility_prediction_interval`) with numeric `lower`, `upper`, and fixed
`coverage=0.80`. Values are decimal ratios: `0.032` means 3.2%, not a formatted
percentage string. Return values and bounds are not clamped; volatility values
and bounds must be non-negative. All model values must be finite.

The horizon is 30 calendar days, not 30 trading observations. Forecast realized
volatility is non-annualized. Asset intervals are empirical prediction intervals
using frozen calibration residuals at nominal 80% coverage, not guarantees or
confidence intervals for a model parameter. This probabilistic outlook is
separate from Aura's deterministic historical analytics and immutable reports.

Public provenance consists of `market_data_as_of`, `market_data_age_days`,
`artifact_version`, `return_model_id`, and `volatility_model_id`. The market-data
date equals the forecast origin, and observations older than four calendar days
are unavailable. `limitations` is a deterministic list stating that estimates
are probabilistic rather than guaranteed, serve educational risk analysis rather
than investment advice, and have nominal interval coverage rather than guaranteed
future observed coverage.

The route delegates to the internal inference service using the application's
existing session and persisted market data. Model loading/caching, feature
construction, approved ARIMA observation-count alignment, and frozen residual
interval application remain internal. No runtime training, recalibration,
candidate fallback, database persistence, or provider request is performed.
Calibration residuals, evaluation metrics, filesystem paths, checksums, Git
hashes, and database configuration are excluded from the public response.
Training/retraining is an offline, manually initiated, versioned workflow;
production inference only consumes the configured frozen artifact version.

Unsupported symbols return a sanitized `404`. Stale data, insufficient history,
missing/corrupt/version-mismatched artifacts, unavailable market data, and invalid
predictions return deterministic `503` messages. Authentication retains existing
`401` behavior, and unexpected failures return a sanitized `500`.

## Portfolio forecasting

`GET /api/forecasting/portfolios/{portfolio_id}/outlook` requires Bearer
authentication and the existing ownership-safe portfolio lookup. It has no
request body or supported query inputs: weights, horizon, historical/as-of
dates, and scenarios cannot be overridden by callers.

The existing baseline resolver supplies all weights. CURRENT uses current USD
valuation, LEGACY preserves saved allocation compatibility, and PLANNED uses
the already-supported proposed-amount target allocation. `baseline_kind`
identifies `current`, `legacy`, or `planned`; component `current_weight` means
the resolved allocation for that mode, not a claim of ownership of planned
assets. All holdings participate, including zero-weight legacy components.
Only allocation-sum drift within absolute `1e-10` is normalized; invalid,
empty, duplicate, or unsupported allocations fail without dropping assets.

Every component delegates to frozen-artifact asset inference using one current
UTC reference date and the existing four-calendar-day freshness rule.
`expected_return_30d` is the arithmetic weighted sum of component expected
returns, without compounding or annualization. Forecast volatility is
`sqrt(w.T @ D @ R @ D @ w)`, where D contains component forecast 30-day realized
volatilities and R is historical correlation. It is not an average of asset
volatilities and does not change deterministic historical analytics.

Correlation uses one batch of persisted adjusted-close histories on or before
the earliest component forecast origin (`correlation_as_of_date`). Log returns
are computed from consecutive stored observations on each asset's own calendar,
then intersected by return observation date across all components. No dates or
prices are filled and no external calendar or provider is used. At least 60 and
at most the latest 252 common return observations are used; their count is
exposed as `correlation_observation_count`. Undefined/non-finite, asymmetric,
out-of-bounds, or materially non-positive-semidefinite matrices are unavailable,
not repaired. Matrix roundoff tolerance is absolute `1e-12`; negative portfolio
variance within `1e-14` squared 30-day volatility units is floored to zero.
Materially negative or non-finite variance fails.

The response includes portfolio ID/name, fixed 30-day horizon, artifact version,
conservative oldest-component `market_data_as_of`, and ordered components.
Components retain the complete asset outlook (including individual origin,
market-data age, model provenance, and nominal 80% intervals), plus weight and
signed `forecast_volatility_contribution` and
`forecast_volatility_contribution_share`. Contributions sum approximately to
portfolio volatility and shares to one when volatility is nonzero. At zero
volatility both contributions and shares are explicitly zero. Negative
contributions are preserved. There is no portfolio prediction interval:
component intervals are not jointly calibrated.

Deterministic limitations state that forecasts are probabilistic, covariance
combines forecast marginal volatility with historical correlations, correlations
may change, and the outlook is educational rather than investment advice.
No forecast is persisted and no model is fitted, updated, recalibrated, or
reselected. One unavailable component fails the whole outlook; no fallback or
partial reweighting is performed.

### Portfolio monetary projection (all four horizons)

Both the 30-day portfolio route and the 7/14/21-day portfolio routes add
`monetary_projection`. CURRENT and PLANNED responses require this object;
LEGACY responses return `null` because saved weights do not establish a money
baseline. Standalone asset responses and asset components have no monetary
projection. No request inputs, database migration or model retraining are added.

The object contains:

- `currency`: CURRENT is `USD`; PLANNED preserves the saved `USD` or `THB` plan
  currency. This is not a caller-selected display-currency conversion.
- `baseline_source`: `current_market_value` or `planned_investment`.
- `baseline_amount`: CURRENT uses the same resolved valuation's
  `total_current_value_usd` (sum of saved latest adjusted-close prices times
  shares), not purchase cost or an old saved analysis. PLANNED uses the same
  resolved allocation's `total_proposed_amount`, without purchasing assets or
  fetching prices/FX for its monetary baseline.
- `expected_change_amount = baseline_amount * expected_return` and
  `estimated_ending_value = baseline_amount + expected_change_amount`. The ratio
  is the unchanged portfolio `expected_return_30d` or weekly `expected_return`,
  never annualized, compounded or scaled from another horizon. For example,
  a USD 10,000 baseline and a 0.03 estimate give USD 300 change and USD 10,300
  ending value. Negative and zero estimates are preserved without clipping.
- `hypothetical`: false for CURRENT, true for PLANNED.
- `assumes_unchanged_fx`: true for THB, false for USD. Applying USD asset-return
  estimates to a THB plan assumes unchanged exchange rates; it is not an FX
  forecast or a conversion using a fabricated rate.
- `valuation_requested_date`, `oldest_price_as_of`, `newest_price_as_of`: CURRENT
  copies the valuation's reference date and actual price-date range. These dates
  are separate from forecast-origin/correlation dates. PLANNED sets all three to
  null because its proposed amount is not a market valuation.
- `limitations`: fixed educational wording about uncertain arithmetic estimates,
  unchanged allocation/holdings, excluded fees/taxes/cash flows, hypothetical
  plans, FX assumptions, and the absence of a portfolio monetary prediction
  interval. Volatility is not converted into a monetary loss estimate. Model
  returns below -100% are not clamped; any negative ending estimate is an
  arithmetic illustration, not a realizable long-only balance.

All three money amounts are finite Decimals serialized as JSON strings to retain
precision. Calculation uses a local high-precision Decimal context, does not
round to cents, and reuses the one authoritative baseline already resolved for
the request; it adds no valuation lookup. Display rounding belongs to clients.
Schemas reject baseline/currency/date mismatches or amounts inconsistent with
the portfolio ratio. Malformed projection outputs use the existing safe `503`
response. Ownership, component completeness, model-quality caveats and all
existing return/volatility/interval fields remain unchanged.

Missing and wrong-owner portfolios return identical `404 Portfolio not found`
responses. Unusable allocations/holding states and unsupported assets return
safe `409` responses. Insufficient common history, stale market data, artifact
failures, invalid forecasts, and unsafe covariance return `503`. Unexpected
failures return a sanitized `500`. Internal paths, exceptions, credentials,
residuals, and training metadata are never public.

## Experimental weekly forecasting

The two additive `/horizons/{horizon_days}/outlook` routes above accept only
`7`, `14` or `21`; other horizons return `422`. Use the original `/outlook`
routes for 30 days; their portfolio response has the additive monetary object
described above, while their existing model fields are unchanged. Bearer authentication, 17-asset
symbol normalization and owner-safe portfolio lookup are unchanged. There is
no request body, user-supplied weights, model selection, historical date or
provider-refresh input. Requests read current persisted observations only.

Weekly estimates use independently trained actual-horizon models, never scaled
30-day output. Return and non-annualized volatility fields are neutral:
`expected_return` and `forecast_realized_volatility` (finite decimal ratios).
Responses include `horizon_days`, `horizon_unit="calendar_days"`, dates/age,
`artifact_version="forecast-weekly-v1-20260917"`, and the corresponding model
IDs. Asset intervals retain `lower`, `upper`, `coverage=0.80` and their existing
names; nominal coverage is not guaranteed achieved coverage.

Every response explicitly includes `experimental=true`,
`predictive_quality_approved=false` and
`quality_status="experimental_educational_not_predictive_quality_approved"`.
Assets/components retain separate `return_warning_codes` and
`volatility_warning_codes` arrays. Approved codes are
`arima_fit_convergence_warning`, `empty_volatility_intervals_counted_as_misses`
and `final_interval_coverage_below_nominal`. Warnings are advisory retained
evidence, not permission to substitute a model or widen frozen intervals.
`limitations` adds mixed-quality, overlapping-label and reused-holdout caveats
to the corresponding established asset/portfolio educational wording.

Portfolio metadata, authoritative CURRENT/PLANNED/LEGACY weights, signed Euler
contributions, 60–252 common-date historical correlation observations and
earliest-origin cutoff retain the 30-day composition policy. Every component
must have the selected horizon and weekly artifact version. One unavailable
component fails the whole outlook. There is no portfolio prediction interval,
daily forecast trajectory, persistence, runtime fitting or forecast AI context.

All 102 model pairs and evidence files must match the externally pinned reviewed
bundle before any model is deserialized. Its build-time `runtime_activated=false`
is preserved as historical evidence, not rewritten by runtime requests. Missing,
corrupt/unapproved artifacts, stale data, insufficient history and invalid model
outputs yield safe `503`. Unsupported assets return `404`; portfolio access is
indistinguishable for missing/wrong-owner IDs (`404`), unusable holdings return
`409`, authentication returns `401`, and unexpected errors are sanitized `500`.
No paths, private residuals, evidence metrics, hashes or credentials are public.
No new database migration is needed. Backend regressions and real smoke checks
remain user-run; web/mobile weekly controls are not enabled in this checkpoint.

## Account Profile V1

`GET /api/auth/me` returns the authenticated account identity plus nullable
`display_name` and `phone_number`, `preferred_language` (`en` or `th`), and
`timezone` (`Asia/Bangkok` or `Asia/Yangon`). Existing accounts receive `en`
and `Asia/Bangkok` during the additive migration; no profile value affects
portfolio calculations or ownership.

`PATCH /api/auth/me` accepts at least one of those profile fields or `email`.
Display name and phone can be explicitly cleared with JSON `null`. Email is
trimmed, case-folded, unique, cannot be cleared, and requires
`current_password` in the same request. Supplying a current password without
an email change is rejected. Successful writes commit once at the request
boundary.

`PUT /api/auth/me/password` accepts `current_password` and a distinct
`new_password`, each at least eight characters. The service verifies the
current Argon2-backed secret, hashes the replacement, stores only the hash,
and returns `204` without a response body. Wrong current passwords return a
sanitized `403`; duplicate emails return `409`. Profile-photo storage,
password reset, notifications, MFA, and revoking sessions for existing accounts remain outside V1.

`DELETE /api/auth/me` requires a Bearer token and a JSON body containing only
`current_password` (at least eight characters). It verifies the current secret
and deletes only the authenticated user, committing once at the API boundary.
The existing database cascades remove that user's CURRENT, PLANNED, and LEGACY
portfolios, holdings, saved analyses/reports, simulations of every mode, and
watchlist entries. Shared market data and other users' owned resources are not
deleted. Success is an empty `204`; wrong passwords return sanitized `403`,
invalid bodies return `422`, and unexpected failures return sanitized `500`
with the transaction rolled back. No user ID override is accepted.

Deletion is permanent. Existing tokens for the deleted user subsequently
return `401` because every authenticated request resolves its subject against
the persisted user. Both clients clear the signed-in session after success.
Device-local preferences/Learn progress and already exported files are not
server-owned data and are not removed by this endpoint. No migration is needed.

## Watchlist V1

Watchlist is an observation-only authenticated resource. It stores only the
owner, normalized supported symbol, item identity, and creation timestamp. It
does not represent ownership, create holdings, or affect portfolio allocation,
analytics, reports, simulations, or agent grounding.

`GET /api/watchlist` returns items in `created_at ASC, id ASC` order. Each item
is enriched from persisted PostgreSQL `market_data`; the request never calls a
market provider. `latest_price` is the newest available `adjusted_close`, and
`latest_price_date` identifies that observation. Daily change compares the
latest observation with the immediately previous available observation, even
across calendar gaps. YTD change compares it with the first available
observation in the latest observation's calendar year. Missing or unsafe
baselines produce `null`; Aura never fills dates or fabricates zero returns.

Only symbols in Aura's code-owned user-asset registry may be added. Symbols are
trimmed and uppercased. A normalized duplicate returns `409`; an unsupported
POST symbol returns `422`; and a missing or non-owned DELETE target returns the
same sanitized `404` response.

## Holding write and compatibility contract

`PUT /api/portfolios/{portfolio_id}/holdings` accepts a complete ordered
current-holding replacement. New current holdings require only the owned
quantity:

| Field | Meaning |
| --- | --- |
| `symbol` | One of Aura's user-selectable USD-quoted assets |
| `shares` | Positive aggregate quantity owned; shares or coin units |
| `invested_amount` | Optional historical provenance for existing/full records |
| `invested_currency` | Optional `USD` or `THB` provenance; complete provenance defaults to `USD` when omitted |
| `purchase_date` | Optional non-future provenance date |

The three provenance fields are either all absent or all complete. Aura never
fabricates them for a quantity-only holding.

The request order becomes the backend-controlled `position`. Symbols must be
unique. Real holdings persist `weight = NULL`; they do not persist current
price, value, allocation, or FX.

During the temporary compatibility period, a returned holding is exactly one
of:

- `LEGACY`: `weight` present and all real fields `null`/absent;
- `CURRENT`: `weight` and `proposed_amount` are `null`, `shares` is present,
  and investment provenance is either fully present or fully absent;
- `PLANNED`: positive `proposed_amount` is present and legacy/current fields
  are `null`.

Legacy portfolios remain available for list, detail, rename, duplication,
deletion, legacy reporting, and legacy simulations. Current valuation is not
available for legacy or planned portfolios. A normal current-holding `PUT`
replacement is the explicit legacy-to-current conversion. Duplication preserves
the source mode.

Planned portfolios persist one `USD` or `THB` plan currency and positive
proposed amounts. Their canonical target weights are derived from proposed
amounts without current prices or FX. Optional estimated shares are a
best-effort preview only and never become saved ownership or analytics input.

## Current valuation

`GET /api/portfolios/{portfolio_id}/valuation` accepts
`currency=USD|THB`; the default is `USD`.

All supported user assets are USD-quoted. For each holding, the backend uses
the latest persisted observation on or before the requested current date:

```text
current_value_usd = shares × asset_price
current_allocation = current_value_usd / total_current_value_usd
```

Required observations may be at most four calendar days old. USD valuation is
independent of FX. THB display additionally uses the internal `THB=X` series,
interpreted as USD/THB (THB per USD). `THB=X` is covered by default/scheduled
market updates but is not a user-selectable holding.

The response includes requested/display currency, requested date, oldest and
newest asset price dates, canonical USD total, display total, optional FX
context, and ordered holding facts/prices/values/allocations.

## Analytics semantics and reports

For current portfolios, analysis resolves the latest USD valuation and dynamic
allocation, then keeps the same owned share quantities across the selected
historical period. Each aligned historical price row produces a portfolio
value; that value series produces portfolio cumulative return, annualized
return, volatility, Sharpe ratio, and maximum drawdown. `purchase_date`, trades,
and cash flows are not reconstructed, so the result is labeled Historical
Portfolio Return rather than actual profit/loss. Current allocation continues
to drive concentration, diversification, and risk contribution against the
historical covariance matrix.

Individual asset return, volatility, maximum drawdown, and Sharpe describe the
asset. Portfolio risk contribution also depends on portfolio weights and
covariance/correlation. A larger investment does not make an asset inherently
more volatile, though a larger allocation can increase its portfolio risk
contribution.

`POST /api/portfolios/{portfolio_id}/reports` keeps `AnalysisPeriod`
(`start_date`, `end_date`) as its JSON body. The optional query parameter
`currency=USD|THB` defaults to `USD`.

Report versions are exact:

- `portfolio-analysis-response-v1`: legacy report behavior;
- `portfolio-analysis-response-v2`: real-holding report with frozen valuation
  context;
- `portfolio-analysis-response-v3`: planned report with frozen proposed amounts
  and target-allocation context.

V2 freezes valuation currency/date, price dates, canonical USD and display
totals, optional FX, holding facts, prices, values, dynamic allocations,
complete analytics, per-asset metrics, per-asset risk classifications, dated
per-asset returns, the fixed-share historical start/end value context, and risk
contribution/rank. Report detail is version-aware.
Opening a saved report reads its JSONB snapshot and never revalues the
portfolio.

V3 freezes plan currency, ordered proposed amounts, exact backend-derived target
weights, complete analytics including per-asset risk classifications and dated
per-asset returns, the hypothetical/non-forecast notice, and an optional
best-effort USD/THB display-conversion observation. Planned analysis does not
require current prices or FX, and estimated shares are not saved in the report.
If FX is unavailable, report creation still succeeds with the original plan
currency only.

V2 and V3 report detail responses derive both portfolio-level
`monetary_metrics` and ordered per-asset `asset_monetary_metrics` from the
immutable snapshot. New V2 portfolio monetary context uses the USD historical
starting value and exact historical ending-minus-starting change; older V2
snapshots without fixed-share value context remain readable but omit the
portfolio monetary object rather than multiplying today's value by a
historical return. Per-asset references are the V2 saved current value or V3
proposed amount. Exact drawdown money uses each dated asset return path; it is
`null` when an older snapshot lacks a verifiable path. These response-only
fields do not trigger revaluation, mutate saved JSONB, or require a migration.
For planned V3 reports, portfolio-level monetary context also includes
`estimated_ending_value`: the saved proposed total plus the saved historical
cumulative-return amount. Clients display this backend-derived value and do
not calculate it locally. V3 detail also returns ordered `currency_views`.
When frozen FX is present these contain complete USD and THB proposed amounts,
portfolio monetary metrics, and per-asset monetary metrics. Opening history
derives both views from the immutable snapshot without a live FX request.

## Simulations and immutable history

Saved simulations may be permanently removed with authenticated
`DELETE /api/portfolios/{portfolio_id}/simulations/{simulation_id}`. Success is
an empty `204`. Missing/wrong-owner portfolios return `404 Portfolio not found`;
missing/wrong-associated simulations return `404 Simulation not found`.
Unexpected failures return sanitized `500 Unable to delete simulation`.
The API commits once; services/repositories do not own transactions. Deletion
removes only the selected snapshot, never the portfolio, reports, market data,
or other simulations. It works for all modes and V1/V2/V3 without restoring or
recalculating the payload. Deleted IDs no longer resolve for detail or AI context.

The three simulation POST request contracts are unchanged. A historical
scenario accepts `scenario_id`. Allocation Change accepts an explicit
historical period and `modified_allocation`; Combined accepts `scenario_id`
and `modified_allocation`.

For real portfolios, the original allocation is the current canonical USD
dynamic allocation at execution. The modified allocation remains the user's
hypothetical percentage input. Simulations continue to test fixed allocations
against historical prices and are not historical share-count backtests.

Existing V1 history remains readable. Exact V2 versions are:

- `historical-scenario-simulation-response-v2`
- `allocation-simulation-response-v2`
- `combined-simulation-response-v2`

Exact planned V3 versions are:

- `historical-scenario-simulation-response-v3`
- `allocation-simulation-response-v3`
- `combined-simulation-response-v3`

V2 history freezes the current valuation baseline used when the simulation was
created. History detail restores that snapshot without current market data,
revaluation, or rerunning the simulation.

V3 history freezes the plan currency, ordered proposed amounts, exact target
weights, complete result, and hypothetical/non-forecast notice. The planned
target allocation is the original baseline for all three modes; Allocation and
Combined keep the user's modified percentages as separate hypothetical input.
V3 detail is also restored without prices, FX, valuation, or recomputation.

## AI contract and grounding

`POST /api/agent/explain` accepts the required `portfolio_id` and `message`,
the existing optional `report_id` and `simulation_id`, and an optional
`history` list for follow-up questions. History contains at most eight messages
(four completed turns), must alternate `user` then `assistant`, and is supplied
again by the client with each request. Aura does not persist chat history in the
backend or database. The web client keeps the current conversation only in
memory, clears it when the user changes portfolios or starts a new chat, and
sends only the latest four completed turns.

Conversation history is untrusted conversational context, not a source of
portfolio facts or calculations. Fresh backend grounding always takes
precedence if prior chat text conflicts with the selected live portfolio or
immutable saved snapshot. Grounding selects:

- live legacy portfolio: saved weights;
- live real portfolio: current USD valuation and dynamic allocation;
- live planned portfolio: proposed amounts and backend target allocation;
- saved Report V2: frozen report snapshot;
- saved Report V3: frozen planned report snapshot;
- saved Simulation V2: frozen current simulation snapshot;
- saved Simulation V3: frozen planned simulation snapshot.

Grounding includes portfolio type, baseline source, and snapshot version.
Planned context excludes internal holding IDs and estimated shares, uses
planned/proposed rather than owned/current language, and adds an explicit
hypothetical/non-forecast/non-order limitation. Provider output that claims a
planned asset is currently owned is rejected.

Saved resources do not require current prices. The agent explains
backend-owned results; it does not calculate financial truth, give personalized
advice, or issue buy/sell recommendations. Provider credentials and provider
implementation details are not part of the public contract.

## Error semantics

| Status | Established meaning |
| --- | --- |
| `401` | Authentication is missing or invalid |
| `403` | The current password supplied for an authenticated sensitive update is incorrect |
| `404` | A private resource is missing or belongs to another user |
| `409` | A requested account email or normalized Watchlist item already exists, or holding state is mixed, incomplete, unsupported, or incompatible with the requested operation |
| `422` | Request validation failed, a profile update is empty/ambiguous, a password replacement is unchanged, a Watchlist POST symbol is unsupported, or established historical analysis/simulation input is unprocessable |
| `503` | Required current asset data is missing/stale, or THB was requested and required FX is missing/stale |
| `500` | Sanitized unexpected internal failure |

Some established routes expose additional intentional statuses, such as AI
provider failures. Consult generated OpenAPI and route-specific tests before
treating the table as exhaustive.

## Transaction boundary

Repositories and services do not own commits. Successful writes commit at the
outer API/request boundary. Valuation is read-only. Reports and simulations
persist one immutable snapshot only after successful calculation at that outer
boundary; failures do not commit partial snapshots.
